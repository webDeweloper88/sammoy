# Обновления приложения LABRIX, протокол 1

Owner → Обновления ПО на главном посту проверяет подписанные выпуски и
запускает сохранённую в БД очередь всех зарегистрированных постов. Обычные посты
обновляются раньше резервного, главный последним. Занятые и недоступные ждут;
недоступный пост не мешает обновить другие готовые посты, но главный ждёт все.
Доступ со второстепенного поста только для чтения. Требуется подтверждение
пароля Owner. Отмена удаляет только ожидающие элементы, уже начатая установка
завершается. Страница подключается снова после перезапуска главного.

Сайт не обновляется от git push. Сборщик создаёт выпуск отдельно, оператор
проверяет его на тестовом посту, добавляет подписанный JSON в Pay → Обновления ПО
как черновик, загружает архив в releases/<sha256>.tar.gz и публикует. Публикация
может быть ограничена объектами. Отзыв запрещает новые установки, но не удаляет
установленную версию. Каталог требует токен активированного поста. Архивы с
опубликованными хешами публичны и не должны содержать секреты или данные мойки.

## Границы первой версии

Только Linux ARM64 Cubie A7A, приложения в Docker, прежний runtime/wallet
протокол 1 и неизменный контракт БД: статические DDL, SQL-файлы и app/db.py. PostgreSQL, ОС, bootloader,
настройки оборудования, роли, .env и секреты пакет не меняет. Бинарные пакеты
включают только docker save по image ID без изменяемых тегов. Ни SQL, ни
произвольные скрипты, ни host-файлы из архива не исполняются. Изменения схемы,
протокола кошелька и обязательных параметров Compose требуют отдельной
процедуры обновления. Совместимость всех промежуточных версий должен подтвердить
выпускающий специалист, автоматический номер протокола не заменяет испытания.

На старые посты службу нужно установить один раз через SSH. Не установленная
служба не мешает работе мойки; Owner показывает необходимость подключения.
До обновления всех старых узлов команды очереди на них не принимаются.

## Доверие и установка

Ключ выпусков отдельный от SSH и commissioning. Закрытый ключ остаётся на
машине сборки, права 0600, резервная копия вне репозитория. Не загружать его на
VPS. На VPS /releases/update-signing.pub.pem и на посту
/etc/labrix-updates/signing.pub.pem находятся только публичные ключи.
Доверенный ключ на пост устанавливается физически/через доверенный SSH;
сайт обновлений не может заменить его. Начальная установка:

    sudo apt-get install python3-cryptography
    sudo deploy/install-software-updates.sh /path/to/signing.pub.pem

В Compose должен быть read-only mount /etc/labrix-updates. После изменения
Compose и приложения перезапуск допускается только на пустом свободном посту.
Для нового IMG зависимость python3-cryptography и публичный ключ необходимо
включить в ОС до экспорта и установить/включить службы обновления. Старый IMG
автоматически не изменяется.

Root-служба принимает только фиксированный запрос на локальном Unix-сокете от
root-процесса. Дважды проверяются подпись, дата, модель платы, номер выпуска,
контракт БД, хеш и размеры. HTTPS загрузка допускается только с pay.labrix.uz,
перенаправления запрещены. Через LAN запросы текущего главного подписаны ключом
объекта и привязаны к поколению и зарегистрированному IP отправителя.

Непосредственно перед остановкой проверяются простой, отсутствие баланса и
незавершённого перевода, подтверждённые OFF и готовность купюроприёмника.
После остановки сверяется постоянный счётчик GPIO; если за время остановки
поступил импульс, установка отменяется и возвращается прежнее приложение.
База и конфигурация копируются после остановки писателей. Автоматический откат
переключает образы, не восстанавливает старую БД поверх новых денег. При новом
активном сеансе откат не перезапускает приложение: требуется сервисная проверка.

## Хранение на 32 ГБ

Проверяется запас: архив + распакованный Docker tar + новые Docker images +
удвоенный текущий размер БД + 1 GiB резерва. Полная копия microSD не создаётся.
После установки/ошибки временные архивы удаляются. Проверенная копия БД,
конфигурация и rollback-теги хранятся 48 часов, чистятся каждый час таймером
sammoy2-update-cleanup.timer. Ошибочные/прерванные установки с needs_review
автоматически не очищаются. Глобальный docker prune не используется.

## Сбой питания и диагностика

Каждое намерение очереди и квитанция root-службы записываются атомарно.
Потерянный ответ разрешается по прежнему UUID, не создаёт новую установку.
Прерванная root-установка после перезапуска получает needs_review и блокирует
следующие. Автоматически повторять остановку, запуск или откат после отключения
питания нельзя: специалист сверяет работающие контейнеры, состояние и OFF,
счётчик GPIO и /var/lib/labrix-updates/jobs/<uuid>/job.json, затем восстанавливает
из записанных previous_images. БД без отдельного решения не восстанавливать.
Контрольная квитанция installed.json меняется только после успешных проверок.

## Создание выпуска

Использовать отдельный каталог за пределами Git для ключа и артефактов.
Скрипт scripts/build-software-release.py требует cryptography и Docker CLI:

    python3 scripts/build-software-release.py keygen --private /secure/signing.pem --public /secure/signing.pub.pem
    python3 scripts/build-software-release.py build --private /secure/signing.pem --number 1 --version 2026.10.23.1 --images images.json --notes notes.json --output /releases/2026.10.23.1

images.json: объект service → проверенный tag/image ID, без postgres.
notes.json: объект ru/uz/en. Номера выпусков никогда не переиспользуются.
Ключи, docker tar, IMG, резервные копии и .env не коммитить.

## Одна команда для подготовки выпуска

На ARM64 машине сборки с Docker и доступом к базовым образам:

    python3 scripts/prepare-software-release.py

Команда запросит следующий уникальный номер выпуска, версию и описание на
ru/uz/en. Сначала сохраните проверенные изменения коммитом: рабочее дерево
должно быть чистым. Собираются все четыре компонента из git archive HEAD;
неотслеживаемые файлы, локальная .env и данные поста не используются.
Образы получают отдельные release-теги, работающие контейнеры не меняются.
Новые зависимости устанавливаются по Dockerfile, поэтому сборке нужен интернет
или предварительно подготовленный кеш. Сборка сама не заменяет проверку на плате.

По умолчанию ключ находится в ../ssh/labrix_updates_signing.pem, результат —
../artifacts/software-releases/<версия>/. Нужен существующий доверенный локальный
образ sammoy2-wash-engine:latest с Python и cryptography: он запускает сборщик
подписи, поэтому на host Python библиотека cryptography не обязательна. Можно
задать --signer-image с доверенным образом. Этот инструмент рассчитан на локальный
Docker через /var/run/docker.sock и Linux CLI /usr/bin/docker; удалённый Docker
context не поддерживается.

На текущей машине, где Docker доступен через локальный служебный помощник:

    python3 scripts/prepare-software-release.py --docker-command 'python3 /home/admin/.cache/sammoy-tools/docker.py'

Для автоматизированного запуска:

    python3 scripts/prepare-software-release.py \
      --number 3 --version 2026.10.23.3 \
      --notes /absolute/path/notes.json \
      --private /absolute/path/signing.pem \
      --output /absolute/path/releases/2026.10.23.3

notes.json: объект с непустыми строками ru, uz, en (до 4000 символов каждая).
Номер и версия в примере не резервируются: перед выпуском сверьте каталог Pay.
--plan проверяет входные параметры и показывает план без сборки и подписи.
Существующий каталог результата не перезаписывается. build.json содержит коммит
и имена образов для проверки происхождения; подписанный release.json и архив
создаются прежним build-software-release.py. Закрытый ключ не копируется в пакет.

После READY испытайте пакет, загрузите архив в releases на VPS, импортируйте
release.json в Pay → Обновления ПО и опубликуйте сначала для тестового объекта.
Автоматической публикации и обновления постов эта команда не выполняет.
