# NV9: журнал импульсов и подтверждение обработки

## Реализовано 10 октября 2026

Helper хранит один постоянный stream UUID и монотонный счётчик в
`data/io-helper/nv9.sqlite3` (в контейнере `/var/lib/sammoy-io/nv9.sqlite3`).
SQLite WAL + synchronous FULL: `/io` получает новый счётчик только после commit.
Перезапуск не меняет UUID и не обнуляет счётчик; повреждённая база не заменяется
пустой автоматически. NV9 thread не продолжает работу после ошибки записи.

Движок хранит подтверждённый счётчик в `app_settings`, ключ `nv9_cursor:<UUID>`.
Под advisory lock он обрабатывает диапазон `previous+1..total`. Платёж,
`cash_events`, обновление/создание сеанса и новый cursor записываются одной
транзакцией PostgreSQL. Повторный диапазон не начисляет деньги. Потерянный ответ
commit сверяется с cursor и остатком в базе перед следующей операцией.
Отрицательный/откатившийся счётчик запрещён. Старый путь начисления по delta не
используется для потока с UUID.

Квитанция имеет ID `nv9:<UUID>:<first>:<last>`. Для перевода NV9 в общий кошелёк
используется этот ID, а для восстановления — `nv9-recovery:<UUID>:<first>:<last>`.
ID исторических платежей не изменены. Защита старых Click/обычных recovery ID
от повторного использования после переустановки остаётся отдельным пунктом.

При обычном приёме деньги поступают в текущий денежный сеанс после commit.
Наличные, обнаруженные при запуске, при неисправности I/O, VIP, блокировке
лицензии или незавершённом переводе карты, сохраняются как `unclaimed` recovery.
Они не исчезают и не выдаются следующему посетителю. Owner видит причину
«Наличные для восстановления» и выполняет существующую операцию восстановления
на денежную карту после проверки принадлежности. Цена диапазона фиксируется
при его первой успешной записи по текущему `billPulseSum` и сохраняется в raw
payload. После перезапуска цена неподтверждённых импульсов определяется текущей
настройкой; журнал не восстанавливает прежнюю цену или владельца.

## Проверки и пределы

4 проверки журнала (включая выход процесса без close), 13 PostgreSQL-сценариев
в disposable `retention_test`, 11 проверок адаптера общего кошелька в
`wallet_test`; 101 основной unit-тест и 6 прежних проверок helper.
В тестах не использованы реальные GPIO или деньги рабочей базы.

Реальные NV9/RS485 пока не подключены для проверки. Нужно измерить длительность
fsync на целевой SD и убедиться, что очередь GPIO не переполняется на импульсах
купюроприёмника. Софт не гарантирует сохранение импульса между физическим фронтом
и commit, не принимает импульсы при выключенном listener/плате и не умеет
аппаратно запрещать приём купюр без подключённого inhibit. Для аппаратной
приёмки нужны проверка inhibit и тесты отключения питания/потери связи на NV9.

## Обслуживание

Не удалять `data/io-helper` при обновлении контейнеров. Не обнулять cursor в
PostgreSQL: это повторно выдаст исторические импульсы. SQLite журнал и
PostgreSQL нужно включить в согласованный backup/restore; WAL нельзя копировать
как обычный один файл в ходе записи. При восстановлении counter ниже cursor
движок откажется работать, а не попытается угадать остаток. Не делать копию
одного stream UUID для двух физических постов. При новой плате без старой
карты памяти создаётся новый UUID; неподтверждённые импульсы со старой SD требуют
отдельного восстановления журнала и проверки Owner.

Запуск после подключения аппаратуры: `docker compose up -d io-helper wash-engine`.
До этого движок остаётся в состоянии недоступного оборудования, без эмуляции.
