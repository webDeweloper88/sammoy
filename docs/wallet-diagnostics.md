# Идентификаторы платежей и диагностика кошелька

Реализовано 10 октября 2026.

## Квитанции

Новые INSERT в `payments` получают сохранённый в `raw_payload.wallet_receipt_id`
ID `payment:<UUID>` через PostgreSQL trigger. Новые recovery получают
`metadata.wallet_recovery_id = recovery:<UUID>`. ID создаётся только при INSERT;
обновление статуса, повторный запуск миграции и изменение номера поста не
пересоздают его. При повторном использовании SQL sequence ID новый платёж
получает другой UUID. Backup базы сохраняет эти ID.

Исторические rows остаются неизменными и используют прежние `post:N:payment:ID`
и `post:N:recovery:ID`. Уже подготовленные задания кошелька сохраняют свои
квитанции и повторяются с теми же ID. NV9 продолжает использовать ID постоянного
потока и диапазона импульсов. Это миграция для новых операций, а не переименование
исторического журнала. Старую финансовую базу нельзя клонировать на новый пост;
восстановление старых незавершённых операций требует исходной идентичности поста.

## Диагностика Owner

В Owner → Кошелёк → «Проверить оба узла» и через
`GET /api/owner/wallet/diagnostics` доступны доступность узлов, роли/поколение,
число операций, незавершённые операции и две SHA-256 сверки:

- журнал всех неотменённых операций;
- фактические карты, pending pointers, квитанции и счётчики дневных VIP-использований.

Данные читаются под существующим site advisory lock. Данные состояния хешируются
страницами по 200 строк с keyset pagination; локальные SQL IDs и времена commit
не включаются, потому что на узлах они могут различаться. Запросы к другим
постам подписаны общим ключом и привязаны к запросу; ключ в ответ не возвращается.
Перед RPC местные locks освобождаются, чтобы две одновременные проверки с разных
узлов не создали взаимное ожидание.

Состояния: не настроен, одна копия, недоступен, разные роли, несовместимый протокол,
незавершённые операции, различие данных, совпадение данных. Это наблюдение на
момент проверки; между снимками может пройти операция. При различии сначала
повторить проверку. Диагностика не списывает деньги, не меняет роли и не даёт
разрешение на failover. `standby_ready` остаётся отметкой последней успешной
синхронизации, а не online-проверкой.

## Проверка при синхронизации

`replica-ready` версии 2 требует совпадения журнала И фактического состояния,
а главный проверяет эти же значения в подписанном ответе. Старого `ok: true`
недостаточно. При отказе отметка готовности сбрасывается; существующий режим
работы с одной копией сохраняется, а новая синхронизация не объявляется успешной.
Перед включением этой проверки нужно обновить wash-engine на обоих узлах.
Не происходит автоматического исправления несовпадающих балансов или удаления
квитанций. Если журнал совпадает, а материализованное состояние повреждено,
catch-up может не исправить его: требуется отдельное контролируемое восстановление.

## Проверки

4 PostgreSQL проверки финансовых IDs: старые данные, повторная миграция,
повтор SQL ID, сохранение NV9 идентичности и UUID recovery.
5 PostgreSQL проверок состояния: карта, квитанция, VIP-день, данные за первой
страницей и отказ/успех readiness proof. Проверки выполняются в отдельной базе.
Unit-проверки покрывают offline, incomplete evidence, смену поколения, pending,
Owner-доступ, освобождение locks перед RPC и отказ старого ready ack.
Браузерная проверка Owner показывает оба узла и проходит UZ/RU/EN.
Два физических поста пока не предоставлены; проверка на реальной сети остаётся.
